# Milestone v1.2 + v1.3 (conversation runtime, presence, reactions, toys, briefs): Code Review Report

**Reviewed:** 2026-11-28T17:27:52Z
**Depth:** deep (cross-file: traced into `xenobot/utils/gemini/response.go`, `xenobot/utils/featherless/converse.go`, `xenobot/utils/chatprompt/ambient.go`, `main.go` dispatcher config, `xenobot/utils/httpserver/server.go`)
**Files Reviewed:** 18
**Status:** issues_found

## Summary

This review covers the conversation pool, briefs, AI emoji reactions, static and cat-sticker reactions, Emoji Consensus, the Highlights Archive, `/inspect`, `/referendum` with its poll tie-breaker, ambient room context, vocative addressing, and the presence settings repository.

**Why Emoji Consensus is flaky.** There are several causes, in order of likely impact:
1. **CR-01.** The per-chat 5-minute cooldown and the per-message once-only latch are claimed before `presenceSetReaction` runs. That call can fail for any of these reasons: the emoji is not in the chat's palette, the pacer sheds the call, the 3 s budget runs out, or Telegram returns a 400. Any failure burns both claims permanently.
2. **WR-03.** The 5-minute chat cooldown is never retried. A message that crosses the threshold during the cooldown only fires if one more reaction arrives after the cooldown ends.
3. **WR-02.** Reaction updates are dispatched concurrently (`main.go:441`, MaxRoutines 200; webhook worker pool at `httpserver/server.go:340-352`). An add/remove pair from one user can be applied out of order and leave phantom members in the distinct-reactor SET.
4. **WR-04.** Everything shares one 3 s context: retract, consensus, archive and PM brief, plus a cold `getChat` behind a 2 s pacer.
5. **IN-01 (operational).** Telegram only delivers `message_reaction` updates when the bot is an administrator. Nothing in the code or the settings page detects this or surfaces it.

**Why Gemini and Featherless misbehave.**
- **CR-03.** Reactions, `/inspect` and the tie-breaker cap output at 512 tokens, and `/referendum` at 768. The code's own comment (`chat_prompt.go:24-26`) says thinking tokens count against the cap. A Gemini MAX_TOKENS answer with only thought parts, or a Featherless reasoning model truncated inside `<think>`, becomes `ErrNoReply`. That error is fed into the shared breaker. Five such errors pause conversations, briefs, toys and reactions for the group for 5 minutes.
- **CR-02.** Featherless conversations send image parts to the model with no text-only fallback. This covers any mention that replies to a photo or sticker. Most Featherless open-weight models are text-only, so they return 400/422, which also feeds the breaker.
- **CR-05.** Reactions and `/inspect` *do* have a fallback. But it writes a global 24 h text-only marker on *any* 400/422, and writes it before knowing whether the text-only retry helps.

**The three hypotheses I was asked to verify:**

| # | Hypothesis | Verdict |
|---|---|---|
| (1) | `chat_react.go` caches a 24 h Featherless text_only marker on any 400/422 vision error, disabling vision across chats | **Confirmed, and slightly worse than stated** (CR-05). The marker is written at `chat_react.go:442`, before the retry's outcome is known, and is kept even when the text-only retry fails too. It is keyed per model, not per chat. `/inspect` inherits it through `chatReactCallProvider` (`chat_inspect.go:219,233`). The conversation path (`chat_run.go:295`) never reads it, which is CR-02. |
| (2) | A blank provider reply with a normal finish reason is counted as a breaker failure via `chatRecordFailure` | **Partly correct.** A reply that turns blank only after `chatFilterReply`/`chatStripReasoning` (`chat_run.go:338-342`) is *not* recorded; the breaker was already cleared at `chat_run.go:319`. A blank that the provider client itself turns into `ErrNoReply` *is* recorded at `chat_run.go:316`, `chat_brief.go:538`, `chat_inspect.go:240` and `chat_polls.go:381`. The client paths are Gemini STOP/MAX_TOKENS with no non-thought text (`gemini/response.go:117-119`) and Featherless stop/length with blank or unclosed-`<think>` text (`featherless/converse.go:216-218,229-233`). See CR-03. |
| (3) | No provider-call duration/token/cache logging | **Confirmed** (IN-06). Only conversation (`chat_run.go:362`) and brief (`chat_brief.go:589`) successes log input/output tokens, at Debug. There is no duration anywhere. Reactions, toys and the tie-breaker log no usage at all. `chatAnswerOf` (`chat_prompt.go:155`) drops `CacheReadTokens` and Gemini's `ThoughtsTokens`, even though both clients parse them (`gemini/response.go:79-83`, `featherless/converse.go:182-189`). |

**Other findings.** The Highlights Archive writes its durable PostgreSQL claim before delivery, inside the shared 3 s context, so a failed copy loses the highlight forever (CR-04). The reasoning-leak guard added in the latest commit drops or truncates legitimate replies and briefs (WR-05). Forum conversation history is not isolated by thread (WR-06). `/inspect` lacks the per-chat cooldown that AGENTS.md documents (WR-08).

The necessity rubric (`~/.claude/gsd-core/references/necessity-review.md`) was read. I could not verify the gotgbot source for how an empty array unmarshals into `ChatFullInfo.AvailableReactions`, because the module cache is absent; IN-02 says so.

## Critical Issues

### CR-01: Emoji Consensus claims the chat cooldown and the per-message latch before the reaction can be set, so any failure suppresses consensus permanently

**File:** `xenobot/modules/presence_reactions.go:322-329` (with `presence_react_api.go:208-231`)
**Issue:** `presenceConsensusClaim` atomically sets `cons:cd` (5 min, per chat) and `cons:done:<msg>` (48 h, per message). `presenceSetReaction` is then called, and its boolean result is discarded. `presenceSetReaction` returns false in any of these cases:
- `presenceAllowedEmoji` fails: the chat restricts reactions, or the cold `getChat` errors or is shed.
- The pacer sheds the call (`MaxWait` 2 s).
- The 3 s `presenceReactionTimeout` has already been consumed upstream (WR-04).
- Telegram returns 400 (`REACTION_INVALID`, a deleted message, and so on).

In every one of these cases both keys are already set. The message can never mirror its consensus, and the whole chat is locked out of consensus for 5 minutes.

Failure scenario: a chat limits reactions to 👍❤🔥 and members pile 🎉 on a message. The threshold is crossed and the claim succeeds. `presenceAllowedEmoji("🎉")` returns false. Nothing is mirrored, and the next message that legitimately crosses the threshold within 5 minutes is also refused. Members see consensus "sometimes work".

**Fix:** Check the palette *before* claiming, and release both keys when the set call fails:
```go
if !presenceAllowedEmoji(ctx, b, chatID, triggerEmoji) || presenceIsLockedDown(chatID) {
    return
}
if !presenceConsensusClaim(ctx, client, chatID, msgID) {
    return
}
authorID := presenceLogAuthorOf(ctx, client, chatID, msgID)
if !presenceSetReaction(ctx, b, chatID, msgID, authorID, triggerEmoji, "cons") {
    // Give both claims back on a fresh, detached context so the next reaction can retry.
    rCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), chatRedisTimeout)
    defer cancel()
    _ = client.Del(rCtx, presenceConsensusCooldownKey(chatID), presenceConsensusDoneKey(chatID, msgID)).Err()
}
```
For a definitive 400 such as REACTION_INVALID or a missing message, keep only the per-message latch, so the bot does not retry forever, and release the chat cooldown.

### CR-02: Featherless conversations send images to the model with no text-only fallback; text-only models fail every image-bearing turn and trip the breaker

**File:** `xenobot/modules/chat_run.go:293-318`, `xenobot/modules/chat_prompt.go:137-152`, `xenobot/modules/chat_watch.go:240-260`
**Issue:**
- `chatJobOf` adds a media ref for the addressed message *and* for the replied-to message: photos, any sticker, GIF/video thumbnails and image documents.
- `chatProcessJob` downloads them, and `chatFeatherlessProvider.converse` forwards every image as an `image_url` part.
- Most Featherless models are text-only and answer 400/422 to multimodal content.
- The error goes to `chatRecordFailure` (`chat_run.go:315`), and the user sees `chat_reply_malfunction`.

The reaction lane already knows how to detect this (`chatIsFeatherlessVisionReject`, `chat_react.go:391`) and degrade to text. The conversation lane neither reads the marker nor retries.

Failure scenario: someone replies "@bot what is this?" to a sticker, with Featherless set to a text-only Llama model. The result is 400, then malfunction, then +1 breaker failure. Five such turns in a group pause conversations, briefs, `/inspect`, `/referendum` and AI reactions (they all check `isPaused`) for 5 minutes. This matches the reported "Featherless problems".

**Fix:** Share the reaction lane's degrade logic, but only mark the model text-only once the retry proves it (see CR-05):
```go
var answer chatAnswer
if job.provider == chatconv.ProviderFeatherless && chatIsFeatherlessTextOnly(ctx, client, chatFeatherlessModelName()) {
    request.Attachments = nil
}
answer, err := chatProviderOf(job.provider).converse(ctx, request)
if err != nil && root.Err() == nil && job.provider == chatconv.ProviderFeatherless &&
    len(request.Attachments) > 0 && chatIsFeatherlessVisionReject(err) {
    textOnly := request
    textOnly.Attachments = nil
    if a2, err2 := chatProviderOf(job.provider).converse(ctx, textOnly); err2 == nil {
        chatMarkFeatherlessTextOnly(ctx, client, chatFeatherlessModelName())
        answer, err = a2, nil
    }
}
```
Do not count a vision reject toward the breaker: it is a capability mismatch, not provider health.

### CR-03: 512/768-token output caps let thinking consume the whole budget; Gemini and Featherless reasoning models return `ErrNoReply`, which feeds the shared breaker

**File:** `xenobot/utils/chatprompt/reaction.go:14`, `xenobot/utils/chatprompt/toys.go:17-22`, used at `xenobot/modules/chat_react.go:520`, `chat_inspect.go:230`, `chat_polls.go:372,691`; recorded at `chat_inspect.go:240`, `chat_polls.go:381`, `chat_run.go:316`, `chat_brief.go:538`
**Issue:** `chat_prompt.go:24-26` states the rule: "Thinking tokens count against it, which is why it is far above the visible reply" (2000 for conversations). Reactions (512), `/inspect` (512), the tie-breaker (512) and `/referendum` (768) ignore that rule.

- **Gemini.** `thinkingLevel` is always `low` (`gemini/request.go:100-103`). When thought parts exhaust `maxOutputTokens`, the candidate ends `MAX_TOKENS` with no non-thought text. `parseReply` then returns `ErrNoReply: blank answer` (`gemini/response.go:117-119`).
- **Featherless.** A reasoning model (R1/QwQ/Qwen3-thinking) truncated inside `<think>` makes `stripLeadingThink` return "", which is also `ErrNoReply` (`featherless/converse.go:216-218,229-233`).

`/inspect` and `/referendum` then call `chatRecordFailure`, which counts toward the 5-failure group pause, and show the malfunction line. Reactions shed silently (`chat_react.go:525-528`), so AI reactions simply "never work" on these providers.

`chatErrorClass` logs this only as "no reply", and `ThoughtsTokens` is never surfaced (IN-06), so the cause is invisible in production.

**Fix:**
- Raise the caps to leave room for thinking. For example, `ReactionMaxTokens`/`InspectMaxTokens`/`TieBreakerMaxTokens` = 2000 and `ReferendumMaxTokens` = 2500, or let `chatRequest` carry a per-call thinking level that the Gemini adapter maps to its lowest level for JSON toys.
- Do not count `ErrNoReply` with a MAX_TOKENS/length finish as a breaker failure:
```go
func chatCountsAsProviderFailure(err error) bool {
    return !errors.Is(err, gemini.ErrNoReply) && !errors.Is(err, featherless.ErrNoReply) && !errors.Is(err, claude.ErrNoReply)
}
// in each caller:
if chatCountsAsProviderFailure(err) { chatRecordFailure(job, err) }
```

### CR-04: Highlights Archive writes its durable PostgreSQL claim and Redis done-latch before delivery, inside the shared 3 s context, so a failed copy or forward loses the highlight forever

**File:** `xenobot/modules/presence_archive.go:364-372, 401-404, 420-465`
**Issue:** `presenceArchiveTrackAndCheck` inserts into `chat_presence_archived` (ON CONFLICT DO NOTHING) and sets `arch:done:<msg>` for 7 days, both *before* `presenceDeliverArchive` runs. Delivery uses the same `runCtx` (3 s, `presence_reactions.go:182`) that consensus already spent its Redis round trips, a DB lockdown read, a possible cold `getChat` and a `setMessageReaction` through the pacer on (WR-04). Delivery errors are only logged at Debug (`:434-436`, `:463-465`).

Failure scenario: a message reaches 5 ❤ and the same reaction also triggers consensus, which uses about 2.8 s. The archive claim commits, and `CopyMessageWithContext` runs with 0.2 s left, then fails with `context deadline exceeded`. The row in PostgreSQL blocks every retry across restarts and replicas, so the highlight never reaches the archive channel. The same happens for a transient 429 or 5xx from Telegram.

**Fix:** Run delivery on its own bounded context derived from `chatContext()`, and give the claim back when delivery fails with a non-definitive error:
```go
deliverCtx, cancel := context.WithTimeout(chatContext(), 10*time.Second)
defer cancel()
if err := presenceDeliverArchive(deliverCtx, b, mru, settings); err != nil && !presenceArchiveDefinitive(err) {
    _ = presence.ReleaseArchived(context.WithoutCancel(ctx), chatID, msgID) // DELETE ... WHERE chat_id=? AND message_id=?
    _ = client.Del(context.WithoutCancel(ctx), presenceArchiveDoneKey(chatID, msgID)).Err()
}
```
`presenceDeliverArchive` must then return its error. Because of the shared deadline, this is a correctness bug and not just a robustness gap.

### CR-05: Featherless "text_only" marker is written on any 400/422, before the retry's outcome is known, globally per model for 24 h (hypothesis 1, confirmed)

**File:** `xenobot/modules/chat_react.go:439-447` (also reached from `chat_inspect.go:219,233`)
**Issue:** `chatIsFeatherlessVisionReject` accepts *any* `HTTPError` with status 400 or 422 that is not `KeyRejected`. That covers more than vision rejection: a context-length overflow, an invalid `max_completion_tokens`, a malformed data URL, a model that is temporarily unservable but answers 400, and similar. `chatReactCallProvider` then calls `chatMarkFeatherlessTextOnly` *before* the text-only retry, and keeps the marker even when that retry also fails. That is proof the 400 had nothing to do with images.

The key `xenobot:cache:featherless_text_only:<model>` is per model, so it is shared by every chat on the server. For 24 h, every AI reaction and every `/inspect` on Featherless drops its image (`chatReactDownloadVision`, `chat_react.go:433-435`). `/inspect` of a photo then sends only `[photo]` to the model and posts a confident verdict about an image it never saw.

**Fix:** Mark the model only once the text-only retry succeeds, and match the error body or type for an image/multimodal rejection where Featherless exposes one:
```go
func chatReactCallProvider(ctx, root context.Context, client *redis.Client, provider string, req chatRequest) (chatAnswer, error) {
    answer, err := chatProviderOf(provider).converse(ctx, req)
    if err == nil || root.Err() != nil || provider != chatconv.ProviderFeatherless ||
        len(req.Attachments) == 0 || !chatIsFeatherlessVisionReject(err) {
        return answer, err
    }
    req.Attachments = nil
    answer2, err2 := chatProviderOf(provider).converse(ctx, req)
    if err2 == nil {
        chatMarkFeatherlessTextOnly(ctx, client, chatFeatherlessModelName())
    }
    return answer2, err2
}
```
Consider a shorter TTL (for example 1 h) so a model upgrade to vision takes effect.

## Warnings

### WR-01: Featherless/Gemini vision degradation is inconsistent across lanes (cross-file)

**File:** `xenobot/modules/chat_react.go:429-437` versus `xenobot/modules/chat_run.go:293-305`, `chat_brief.go` (no media), `chat_polls.go` (no media)
**Issue:** The reaction and `/inspect` lanes consult the text-only marker, but the conversation lane never does. Once reactions have learned that the model is text-only, conversations keep sending images, failing and counting breaker failures. The breaker pause that results also silences the reaction lane (`chat_react.go:488`), so the two lanes interfere.
**Fix:** Move the read/degrade/mark logic into one helper (`chatConverseWithVisionFallback`) that `chatProcessJob`, `chatReactProcessJob` and `chatInspectProcess` all call, together with CR-02 and CR-05.

### WR-02: Concurrent dispatch of `message_reaction` updates can apply one user's add and remove out of order, leaving phantom members in the consensus and archive SETs

**File:** `xenobot/modules/presence_reactions.go:289-317`, `presence_archive.go:336-348`; concurrency from `main.go:438-442` (MaxRoutines 200) and `xenobot/utils/httpserver/server.go:340-352` (worker pool)
**Issue:** Each update is handled in its own goroutine. Suppose a user taps 🔥 and then un-taps it within a second. Update A has old=[] and new=[🔥]; update B has old=[🔥] and new=[]. They can run as B's SREM followed by A's SADD. The user then stays in `cons:u:<msg>:🔥` for 48 h (and in `arch:u:<msg>` for 72 h) although they have no reaction.

The reverse ordering under-counts. If a user switches 👍 → 🔥 → 👍 quickly, the result can leave them in both sets or in neither. Consensus fires with fewer real reactors than the threshold, or fails to fire with enough of them.
**Fix:** Treat each update's `new_reaction` as the user's absolute state, and order the updates per user with a monotonic stamp. For example, store `cons:last:<msg>:<user>` = `update_id` and apply only if the new update_id is larger, in the same Lua script:
```lua
local last = tonumber(redis.call('GET', KEYS[2]) or '0')
if tonumber(ARGV[4]) <= last then return redis.call('SCARD', KEYS[1]) end
redis.call('SET', KEYS[2], ARGV[4], 'EX', ARGV[3])
-- then SADD/SREM as today
```
(`ctx.UpdateId` is monotonic for a bot.)

### WR-03: The per-chat 5-minute consensus cooldown is not a queue; a message that crosses the threshold during the cooldown only fires if another reaction arrives after it expires

**File:** `xenobot/modules/presence_reactions.go:314-327, 36-38`
**Issue:** The threshold is evaluated only when a reaction is *added*, and the claim is refused while `cons:cd` exists. In an active chat, two popular messages two minutes apart get one mirror. The second message only mirrors if a reaction lands after the cooldown, and the most common pattern (a burst of reactions in the first minute, then silence) means it never does. From the user's side this is "sometimes works, sometimes doesn't".
**Fix:** Either shorten the default cooldown and document it on the page, or record crossed-but-cooldown-blocked messages (`ZADD cons:pending score=now member=msgID`) and drain them on the next reaction or message in the chat after the cooldown. At minimum, expose the cooldown on page `pr` so admins understand the behavior.

### WR-04: One 3 s context is shared by retract, consensus, archive and PM brief, including a live `getChatMember`, two DB reads, a cold `getChat` and a paced `setMessageReaction`

**File:** `xenobot/modules/presence_reactions.go:182-185, 212-228`; `presence_react_api.go:93-126, 219-225`
**Issue:** `presenceReactionTimeout` = 3 s bounds the whole fan-out. On one reaction, the following can run in sequence:
- Retract: `presenceIsAdmin`, a live call when the cache is cold.
- Consensus: N Redis scripts, `presenceIsLockedDown` (a PostgreSQL read), the claim, `presenceLogAuthorOf`, `presenceAllowedPalette` (on a miss, `getChat` behind a pacer with `MaxWait` 2 s) and `setMessageReaction` (pacer again).
- Archive: Redis, a PostgreSQL claim, copy/forward.
- PM brief: settings, audience (live admin check), Redis, log read.

Whatever runs later gets the leftover budget. Combined with CR-01 and CR-04, a slow early step corrupts later steps' durable state.
**Fix:** Give each sub-feature its own deadline derived from `chatContext()`, for example `context.WithTimeout(chatContext(), 3*time.Second)` per call, and keep the handler-level context only for the shared reads (settings, staff gate).

### WR-05: Reasoning-leak guard (`chatStripReasoning`) drops or truncates legitimate replies, briefs, verdicts and poll text

**File:** `xenobot/modules/chat_leak.go:16-32`; applied through `chatSanitizeText` (`chat_send.go:63-68`) to conversations, briefs (`chat_brief.go:560`), `/inspect` verdicts (`chat_inspect.go:256`) and referendum text (`chat_polls.go:516,523`)
**Issue:** `chatDraftCue` matches ordinary phrases such as `maybe add`, `keep it short`, `the user wants` and `I need to reply`. With no "Final:" marker, the whole text becomes "".
- **Conversation.** A member asks "how do I improve my soup?" and the bot answers "Maybe add some salt…". The reply is dropped, `chat_reply_malfunction` is posted, and the failure is counted (`chat_run.go:339-342`).
- **Brief.** A summary that quotes a member ("Alex said maybe add a rules channel") is blanked entirely, and `brief_malfunction` is posted.
- **Truncation.** `chatFinalMarker` matches any line starting with `Answer:`, `Reply:`, `Output:` or `Response:`, which is common in a brief of a quiz or Q&A thread. When a draft cue appears earlier in the text, *everything before the last such line is silently discarded* and a truncated brief is posted.
**Fix:** Restrict the guard to the conversation lane, anchor it to the start of the text (a leak always opens with planning), and require at least two distinct cues:
```go
func chatStripReasoning(text string) string {
    head := text
    if len(head) > 400 { head = head[:400] }
    cues := chatDraftCue.FindAllStringIndex(head, -1)
    if len(cues) < 2 || cues[0][0] > 80 { return text }
    ...
}
```
Use a non-reasoning sanitize (`chatSanitizeLinks`) for briefs, verdicts and polls.

### WR-06: The conversation transcript is chat-wide, not per forum topic, while ambient context is thread-isolated

**File:** `xenobot/modules/chat_history.go:56-80, 85-109` (keys `chatHistoryKey(chatID)`); used at `chat_run.go:291`
**Issue:** In a forum supergroup, a mention in topic B receives the last 12 lines of the bot's conversation from topic A as "recent conversation". The model answers off-topic and leaks one topic's content into another, which can matter for private topics such as an admins-only topic in a public forum. The ambient path deliberately isolates threads (`chatLogRecentThread`), and briefs do too (`chatBriefStretch`). The transcript does not.
**Fix:** Include `threadID` in `chatHistoryEntry` and filter on read, or key the transcript per thread: `chatKeyPrefix + "{" + chat + "}:h:" + strconv.FormatInt(threadID, 10)`. `applyChatEnabled` must then delete the per-thread keys too, for example by tracking them in a SET.

### WR-07: AvailableReactions cache treats any zero-length list as "all reactions allowed"

**File:** `xenobot/modules/presence_react_api.go:107-109`
**Issue:** `len(info.AvailableReactions) == 0` covers both cases: the field omitted (all allowed, per the Bot API) and the field present but empty, which is what Telegram returns when an admin disables reactions entirely. In a chat with reactions disabled, the following happens:
- Every AI reaction job pays a full LLM call and then `setMessageReaction` fails.
- `REACTION_INVALID` evicts the cache, so the next message re-fetches `getChat`.
- Static and cat-sticker rules burn their cooldowns.

*I could not verify this against gotgbot's `ChatFullInfo` unmarshaler, because the module cache is not present. Confirm whether an empty JSON array decodes to nil or to `[]ReactionType{}`. If it decodes to nil, the distinction is lost before this code and must be recovered from the raw response.*
**Fix:** Distinguish nil from empty (`info.AvailableReactions != nil && len(...) == 0` means none allowed, and returns `(nil, false)`). On `REACTION_INVALID`, cache a short negative entry instead of only deleting, so a disabled chat is not re-fetched on every message.

### WR-08: `/inspect` has no per-chat cooldown, although AGENTS.md documents one for both toys

**File:** `xenobot/modules/chat_inspect.go:266-288` versus `chat_polls.go:407-415`
**Issue:** AGENTS.md (Phase 35) says both `/referendum` and `/inspect` share `chatToyChatCooldown` (30 s). `chatInspectReserve` applies only the user cooldown. Several members can each run `/inspect` back to back. Each run is a vision download plus a provider call, up to the 30/chat/hour budget, which floods the chat with verdict messages. The behavior and the documentation disagree.
**Fix:** Add the same chat-cooldown claim as `chatReferendumReserve` before the user cooldown, or update AGENTS.md to state that `/inspect` intentionally has no chat cooldown.

### WR-09: AI reaction gate burns the chat and user cooldowns before the job runs; shed, capped and failed jobs still consume 8-15 minutes of quiet

**File:** `xenobot/modules/chat_react.go:128-158, 346-354, 484-528`
**Issue:** The Lua gate resets the gap counter and sets `ai:cd:chat` (8-15 min) and the user cooldown at enqueue time. The job can still end in any of these ways:
- The queue is full (`chatPresenceEnqueue` sheds).
- The chat is locked down.
- The breaker is paused.
- The budget is capped.
- The palette fetch fails.
- The provider errors (CR-03 makes this frequent on Gemini and Featherless).
- The model answers NONE.

In each case the chat gets nothing for the full cooldown. On Gemini with CR-03, a "medium" chat produces roughly one attempt every 8 minutes and every one of them fails. This compounds the "AI reactions never appear" symptom.
**Fix:** Take only the gap and roll at enqueue. Set the chat and user cooldowns after a successful `presenceSetReaction`, or release them on shed and error. At minimum, release them when the job is shed before any provider call.

## Info

### IN-01: Operational — `message_reaction` updates are delivered only when the bot is a chat administrator; nothing detects or surfaces this

**File:** `xenobot/modules/presence_reactions.go:98-100`, settings page `pr` (`settings_presence.go`, no admin check)
**Issue:** Per the Bot API docs ("The bot must be an administrator in the chat … to receive these updates"; verify against the current Bot API), consensus, retract, archive and the ✍ PM brief are silently dead in any group where the bot is not an admin. From the owner's point of view this looks exactly like "sometimes works". There is no code bug, but there is no signal either.
**Fix:** On page `pr`, show a status line (as `settings_mreq_here_*` does) when `chat_status.IsBotAdmin` is false, and note the requirement in the help text.

### IN-02: Static and cat-sticker reactions run synchronously in handler group 8 and can delay groups 9-14 by up to 5 s

**File:** `xenobot/modules/reactions.go:620-636`
**Issue:** A matching rule makes `checkReactions` do the following inline: a PostgreSQL lockdown read, Redis claims, a possible cold `getChat` and a paced `setMessageReaction` (`MaxWait` 2 s plus a 5 s call bound, capped at `staticReactTimeout` 5 s). Filters (9), pins (10), the log channel (11), the late flood counter (12), the conversation watcher (13) and the message log (14) all wait. Under a 429 block, conversation replies stall behind keyword reactions.
**Fix:** Hand the set call to the presence lane (`chatPresenceQueue`) or a small dedicated goroutine pool, and keep only the pure match and the claim inline.

### IN-03: `checkReactions` recovers a panic but returns `nil`, which skips the rest of group 8

**File:** `xenobot/modules/reactions.go:596-601`
**Issue:** The recovered path returns the zero value `nil`. In this gotgbot that leaves group 8, so `reportWatch` (the `@admin` watcher in the same group) is skipped for that message if Reactions registered first. Other watchers use a named result preset to `ext.ContinueGroups` (see AGENTS.md).
**Fix:** `func (m moduleStruct) checkReactions(...) (result error) { result = ext.ContinueGroups; defer error_handling.RecoverFromPanic(...) ... }`.

### IN-04: Ambient and reaction context scans only the newest 50 log entries, with no time bound

**File:** `xenobot/modules/chat_log.go:39-40, 189-218`; used by `chat_run.go:381` (limit 8) and `chat_react.go:402` (limit 5)
**Issue:** There are two effects:
- In a busy multi-topic forum, the target thread often has zero of the last 50 entries, so ambient context is silently empty even when the feature is on.
- In a quiet chat, entries up to the 7-day log TTL are presented under the label "Recent room chatter", which misleads the model with stale context.

`/referendum` uses the unbounded `chatLogRecent` instead (`chat_polls.go:294`), which is inconsistent.
**Fix:** Add a recency cutoff (for example `entry.At >= now-2h`), and scan by thread more deeply (a 200-entry bound) or keep per-thread rings.

### IN-05: Vocative detection never matches real Ukrainian or Russian vocative forms

**File:** `xenobot/utils/chatprompt/ambient.go:74-128` (called from `chat_watch.go:83`)
**Issue:** The candidates are nominative only ("Ксенобот", "Xenobot"), and the next rune must be a delimiter. "Ксеноботе, …" (the Ukrainian vocative case) and "Ксеноботик, …" therefore fall through to `continue`. The feature is named and documented as vocative addressing, but the commonest way a Ukrainian speaker addresses the bot does not trigger it.
**Fix:** Add the vocative and diminutive forms to the candidates ("Ксеноботе", "Кзеноботе", "Ксеноботику") and test them in `ambient_test.go`.

### IN-06: No provider-call duration, cache-token or thinking-token telemetry (hypothesis 3, confirmed)

**File:** `xenobot/modules/chat_prompt.go:155-164`, `chat_run.go:362`, `chat_brief.go:589`, `chat_react.go:524-530`, `chat_inspect.go:233`, `chat_polls.go:374,693`
**Issue:**
- `chatAnswerOf` copies only the input and output token counts. It drops `CacheReadTokens` (parsed by all three clients) and Gemini's `ThoughtsTokens`.
- No call site measures latency.
- Reactions, toys and the tie-breaker log no usage at all.
- Errors are logged only as `chatErrorClass` ("no reply").

The CR-03 thinking exhaustion and the Anthropic prompt-cache hit rate on the static persona are both invisible.
**Fix:** Carry `CacheReadTokens` and `ThoughtsTokens` in `chatAnswer`. Wrap `converse` in one helper that logs at Debug, with IDs only: `provider, lane, duration_ms, in, out, cache_read, thoughts, outcome`. Add aggregate counters to `/stats`.

### IN-07: Retraction authorization loses the author when consensus overwrites `bot_react` with author 0 (message log off)

**File:** `xenobot/modules/presence_reactions.go:328-329`, `presence_react_api.go:233-238`
**Issue:** When the message log is off, `presenceLogAuthorOf` returns 0. A consensus mirror on a message that already had a static or AI reaction (which recorded the real `AuthorID` from the update's sender) overwrites `bot_react` with `AuthorID: 0`. The message's author can then no longer 👎-retract; only admins can.
**Fix:** Before writing, keep an existing record's non-zero `AuthorID` (read-modify-write in a small Lua script), or pass the author through from the triggering reaction context when it is known.

### IN-08: ✍ PM brief consumes its 60 s presence cooldown even when the shared brief cooldown then sheds the job silently

**File:** `xenobot/modules/presence_reactions.go:390-412`, `chat_brief.go:465-468`
**Issue:** `presencePMBriefCooldownKey` is claimed first. The job then also claims `chatBriefCooldownKey` (20 s, shared with `/unrollshort`). A user who ran `/unrollshort` 10 s earlier gets nothing for the ✍ reaction, and their ✍ cooldown is spent for 60 s.
**Fix:** Skip the brief cooldown for `silentPM` jobs (the presence cooldown already gates them), or check it before claiming the presence key.

### IN-09: Poll tie-breaker makes an unbudgeted provider call synchronously in a dispatcher goroutine (up to 60 s)

**File:** `xenobot/modules/chat_polls.go:546-562, 674-710`
**Issue:** `handlePollUpdate` runs the AI call inline under `chatToyJobTimeout` (60 s). It reserves no `toy:b` budget and never records breaker failures, so a failing provider is retried on every tied poll. It is bounded only by one claim per poll ID, which is acceptable, but it also holds a dispatcher slot for the whole call.
**Fix:** Enqueue the tie-breaker on `chatToyQueue` after claiming the tie, and reserve one budget unit (falling back to the canned text when capped).

### IN-10: `chatInspectQuotedTurn` never produces anything, because Telegram does not nest `reply_to_message` inside a `reply_to_message`

**File:** `xenobot/modules/chat_inspect.go:127-144, 182`
**Issue:** Per the Bot API, the Message in `reply_to_message` "will not contain further reply_to_message fields even if it itself is a reply". `extraction.ReplyTarget(reply)` is therefore always nil and `job.quoted` is always nil. The code path runs but is dead (Code Quality, not necessity).
**Fix:** Remove `chatInspectQuotedTurn` and the `quoted` field of `chatInspectJob` (the Bot API never delivers the nested target, so there is nothing to resolve).

### IN-11: Already-defended-elsewhere — `presenceHandleArchive` repeats every guard its only caller has already applied

**File:** `xenobot/modules/presence_archive.go:380-387`
**Category:** necessity
**Issue:** `presenceHandleArchive` has exactly one caller, `presenceDispatchReaction` (`presence_reactions.go:222-223`; there are no test callers). By the time it runs, the caller has already guaranteed every condition it re-checks:
- `b != nil` and `mru.Chat` type allowed (`presence_reactions.go:190-194`).
- `mru.User != nil` and `!IsBot` (`:194`, `:216`).
- `!presenceIsStaffGroup(chatID)` (`:201`).
- `ArchiveEnabled && ArchiveChatID != 0` (`:222`).

The repeated `presenceIsStaffGroup(chatID)` is an extra Redis read per reaction inside the shared 3 s budget. (`presenceIsStaffGroup(settings.ArchiveChatID)` is not redundant and should stay.) This is judgment-level, because the function is package-visible and a future caller could rely on the guards.
**Fix:** Drop the duplicated checks, or keep them and document the function as a defensive public entry point.
