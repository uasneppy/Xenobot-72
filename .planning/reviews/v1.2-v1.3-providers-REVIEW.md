# Milestone v1.2 + v1.3: Code Review Report (Gemini and Featherless provider clients)

**Reviewed:** 2026-11-28T12:00:00Z
**Depth:** deep
**Files Reviewed:** 13
**Status:** issues_found

## Summary

This review covers the v1.2 and v1.3 provider leaf clients (`gemini`, `featherless`, the `claude` Converse path) and the `chatprompt` builders. It also traces how the runtime in `xenobot/modules` uses them. I read every scoped file in full and followed each error and answer into its callers: `chat_prompt.go`, `chat_run.go`, `chat_brief.go`, `chat_inspect.go`, `chat_polls.go`, `chat_react.go`, `memberreq_ai*.go` and `raid_ai_image.go`.

The leaf invariant holds. The gemini, featherless and claude packages import only the standard library, and chatprompt imports only the standard library plus `xenopersona`. No error string carries the API key or the request URL: `transportError` unwraps `*url.Error`, and `newHTTPError` scrubs the key from every field it takes from the body.

**The three hypotheses from the other agent are all confirmed against this checkout.** None of the fixes they describe are present.

1. **Text-only cache is too broad (WR-02, WR-03).** Any Featherless 400 or 422 on a request with an image marks the model "text-only" for 24 hours, for every chat. The mark is written before the text-only retry has shown that the image was the cause. The conversation path never reads the cache and has no fallback of its own.
2. **Blank answers trip the breaker (WR-01).** A blank answer with a normal finish (`STOP`, `MAX_TOKENS`, `stop`, `length`) becomes the generic `ErrNoReply`, and so does Featherless's documented `no choices` answer. The conversation, brief, `/inspect` and `/referendum` paths record it with `chatRecordFailure`, so it counts toward the 5-failure group pause. The repository's own research notes say this must never happen.
3. **Observability is dropped (WR-06).** Cache-read tokens and Gemini thought tokens are parsed and then discarded at `chatAnswerOf`. No provider call logs how long it took.

**New findings:**
- **Critical (CR-01).** Featherless `stripLeadingThink` only strips reasoning that begins with an opening `<think>` tag. Some chat templates (QwQ, DeepSeek-R1 distills) put `<think>\n` into the prompt, so the model's output starts with the reasoning and only has the closing `</think>`. That reasoning reaches the group unchanged, which breaks the function's own guarantee.
- **Classify token cap (WR-04).** The Featherless classify cap is 256 tokens, below the 512-token floor the team measured for reasoning models.
- **Shared model for images (WR-05).** Raid image checks use the same `FEATHERLESS_MODEL` as the name checks. A text-only model, such as the package's own example `Qwen/Qwen3-32B`, fails every image check.
- **No transport retry (WR-07).** The client never retries a transport error, so a transient TLS failure counts toward the breaker.

**Cross-file note:** WR-01, WR-02, WR-03, WR-05 and WR-06 sit at module call sites outside the 13-file scope (`xenobot/modules/*`). They are listed under their real paths because each describes how a scoped client's error or answer is consumed. `files_reviewed_list` stays at the 13 scoped files.

**Unverified items:** IN-01 to IN-04 and IN-06 rest on how Google and Featherless behave, which I recall from outside the repository; the repository does not prove it. They are Info and marked "unverified against provider docs; verify before fixing".

**Necessity:** I found no necessity issues (`necessity: 0`). `gemini.Options` looks unused in production, but the spike tool uses it (`.planning/spikes/001-reaction-picker-tokens-and-format/main.go:495`), so it is not a necessity finding.

## Narrative Findings (AI reviewer)

## Critical Issues

### CR-01: Featherless reasoning leaks to the group when the model omits the opening `<think>` tag

**File:** `xenobot/utils/featherless/converse.go:223-237` (also affects `classify.go:190`)

**Issue:** `stripLeadingThink` strips reasoning only while `strings.HasPrefix(s, "<think>")` holds. Its doc comment promises that "raw reasoning never leaks to a group chat", but it returns `"Okay, the user wants…</think>\n\nanswer"` unchanged.

This happens whenever the chat template appends `<think>\n` to the generation prompt, which the QwQ-32B and DeepSeek-R1-Distill templates do, and Featherless serves the model without a server-side reasoning parser. The model's content then opens straight with the reasoning and contains only the closing tag.

Spike 003 (`.planning/spikes/003-reaction-vision-media/README.md:96`) and spike 002 (`.planning/spikes/002-reaction-abstention-and-persona/README.md:91`) both record Featherless writing chain-of-thought into `content`.

`parseConverseReply` returns that text as `OutcomeAnswered` (`converse.go:216`). The runtime then only runs `chatStripReasoning` (`xenobot/modules/chat_leak.go:23`), and that only drops a draft when it matches English cue phrases ("the user is asking", "keep it short", …).

**Failure scenario:** A member asks something in Ukrainian. `CHAT_FEATHERLESS_MODEL=Qwen/QwQ-32B` answers with "Гаразд, учасник питає… Персона каже, що я… </think> Відповідь". The reasoning has no English cue phrase, so the whole reasoning block is posted in the group: the `</think>` tag, paraphrased persona and archive instructions, and comments on members.

**Fix:** Cut at the last closing tag when one is present without an opening tag, and compare the tag case-insensitively. Fully untagged prose reasoning, which spike 002 also saw, cannot be fixed in the client. Document that as a stated limit, and push for models or servers that use a reasoning parser.

```go
func stripLeadingThink(s string) string {
	s = strings.TrimSpace(s)
	for hasPrefixFold(s, "<think>") {
		end := indexFold(s, "</think>")
		if end < 0 {
			return ""
		}
		s = strings.TrimSpace(s[end+len("</think>"):])
	}
	// A template that injects "<think>\n" into the prompt yields
	// "reasoning…</think>answer" with no opening tag.
	if end := lastIndexFold(s, "</think>"); end >= 0 {
		s = strings.TrimSpace(s[end+len("</think>"):])
	}
	return s
}
```

Add test cases next to `featherless_test.go:227`, for example `chatAnswer("stop", "plan…</think>\n\nAnswer.")` should give `"Answer."`. Add a matching `parseVerdict` case.

## Warnings

### WR-01: Blank and "no choices" answers count as provider failures and pause the group

**Files:**
- Clients:
  - `xenobot/utils/gemini/response.go:87-92` (no candidates), `:105-106` (unknown finish), `:117-120` (blank after STOP or MAX_TOKENS)
  - `xenobot/utils/featherless/converse.go:191-193` (no choices), `:216-219` (blank after stop or length, or an unclosed `<think>`)
  - `xenobot/utils/claude/converse.go:266-269`
- Consumers:
  - `xenobot/modules/chat_run.go:307-317`
  - `xenobot/modules/chat_brief.go:531-538`
  - `xenobot/modules/chat_inspect.go:233-240`
  - `xenobot/modules/chat_polls.go:374-381`

**Issue:** Every "the provider answered, but the answer had no usable text" case wraps the same `ErrNoReply` as an unreadable body. The cases are:
- Gemini thinking that used up `maxOutputTokens` (only `thought:true` parts come back)
- Gemini's empty answer with finishReason STOP
- Featherless `no choices`
- Featherless reasoning cut before `</think>`

Every runtime path except the reaction lane passes this to `chatRecordFailure`. `chatRecordFailure` calls `breaker.countFailure`, and five failures pause that group's conversations, briefs, `/judge`, `/inspect` and `/referendum` for 5 minutes. The user also gets the malfunction line.

The repository's research notes forbid this:
- `PITFALLS.md:118` and `PITFALLS.md:289` say these answers must never trip the breaker.
- Spike 003 recorded Featherless returning `no choices` after 12.9 s.
- `STACK.md:222` and `PITFALLS.md:104` record Gemini thinking starvation that causes `ErrNoReply`.

`/inspect` and `/referendum` use only 512 and 768 output tokens (`chatprompt/toys.go:17-20`) and `/inspect` sends an image, which makes thinking starvation more likely. The tests pin the current behavior: `gemini_test.go:147` and `:158`, and `featherless_test.go:227`, `:230`, `:234` and `:236`.

**Failure scenario:** A busy group uses Gemini. Three `/inspect` calls on photos end with MAX_TOKENS and thought parts only, and two Featherless-style "no choices" answers arrive. That is five failures, so every AI feature in the group is paused for 5 minutes, although the provider is healthy.

**Fix:** In each client, add a separate sentinel for an empty answer, for example `ErrEmptyAnswer` that wraps `ErrNoReply` so `errors.Is` keeps working. Set it for a blank STOP, MAX_TOKENS, stop or length answer and for "no choices". Then, in `chatRecordFailure` callers (or in `chatErrorClass` and its breaker counterpart), treat it as neither a failure nor a success. Count it in a separate "empty" counter, and optionally retry once inside the client. For Gemini, a blank MAX_TOKENS with `ThoughtsTokens > 0` should be reported as thinking starvation so operators can raise the cap.

### WR-02: Any Featherless 400 or 422 with an image disables vision for that model for 24 hours, fleet-wide

**File:** `xenobot/modules/chat_react.go:391-396`, `:439-446` (called from `chat_react.go:524` and `chat_inspect.go:233`)

**Issue:** `chatIsFeatherlessVisionReject` accepts any 400 or 422 whose key was not rejected. `chatReactCallProvider` then calls `chatMarkFeatherlessTextOnly` before the text-only retry, and never undoes the mark if the retry fails the same way. The mark is a `SET` keyed only by model name with a 24-hour TTL, so it turns off vision for every chat on every replica.

These 400s have nothing to do with vision:
- context length exceeded (ambient chatter plus history plus image)
- `max_completion_tokens` larger than the remaining context
- a chat template that rejects the `system` role (Gemma-family templates raise "System role not supported")
- a malformed or oversized image payload
- an unsupported `response_format`

`featherless/errors.go` keeps `Type`, `Code` and `Message`, but none of them is consulted.

**Failure scenario:** One `/inspect` on a long thread overflows the model's context and gets a 400. Vision is now off for every group for 24 hours. The text-only retry then fails with the same 400 and is recorded as a breaker failure (`chat_inspect.go:240`).

**Fix:** Mark text-only only when the text-only retry succeeds and the first error's `Message` or `Code` names images or multimodal input. Otherwise return the original error without marking:

```go
answer, err := chatProviderOf(provider).converse(ctx, req)
if err != nil && … && chatIsFeatherlessVisionReject(err) {
	textOnly := req
	textOnly.Attachments = nil
	answer2, err2 := chatProviderOf(provider).converse(ctx, textOnly)
	if err2 == nil && featherlessErrMentionsImage(err) {
		chatMarkFeatherlessTextOnly(ctx, client, chatFeatherlessModelName())
	}
	return answer2, err2
}
```

Also consider a shorter TTL, such as 1 hour.

### WR-03: The conversation path has no text-only fallback for Featherless

**File:** `xenobot/modules/chat_run.go:293-307` (with `xenobot/modules/chat_prompt.go:137-146`)

**Issue:** Only the reaction and `/inspect` paths read the text-only cache and fall back. The conversation path builds attachments through `chatDownloadMedia` and calls `chatProviderOf(job.provider).converse` once. On a 400 or 422 it records a breaker failure (`chat_run.go:315`). `chatFeatherlessProvider` passes every JPEG, PNG or WebP to `Images` without checking whether the model can take images.

**Failure scenario:** `CHAT_FEATHERLESS_MODEL=Qwen/Qwen3-32B`, a text-only model (`.planning/spikes/003-reaction-vision-media/README.md:30`). Every mention that carries a photo, sticker or GIF thumbnail fails with a 400 and shows the malfunction line. Five such turns pause the group, and text-only mentions in that group are paused with them.

**Fix:** In `chatProcessJob`, read `chatIsFeatherlessTextOnly` before `chatDownloadMedia`. Reuse the corrected `chatReactCallProvider` from WR-02, or a shared helper, so a conversation with an image falls back to text and caption.

### WR-04: The Featherless classify cap of 256 tokens is below the measured 512 floor for reasoning models

**File:** `xenobot/utils/featherless/classify.go:14`, `:97`, `:143`, `:183-184`

**Issue:** `Classify` and `ClassifyNames` send `max_completion_tokens: 256`, and `parseVerdict` refuses any finish other than `stop`. The repository's own measurements show reasoning models on Featherless spend that budget on `<think>` or prose:
- `STACK.md:222`: "`384` still truncated on Featherless; `512` achieved 0% truncation"
- `STACK.md:223`: "Featherless `256`-token failures"
- `PITFALLS.md:104`

The resulting `finish length` is `ErrNoVerdict`. That is recorded as a provider failure (`memberreq_ai.go:687-695`, `raid_ai_image.go:459-460`), it spends a budget unit, and it leaves an unknown verdict.

**Failure scenario:** `FEATHERLESS_MODEL=Qwen/Qwen3-32B` with thinking on by default. Most name checks end with `finish length` while still inside `<think>`. Five failures pause name checks for the group, and the hourly budget keeps draining with no verdicts.

**Fix:** Raise `maxClassifyOutputTokens` to at least 512, matching `chatprompt.ReactionMaxTokens`. Treat `length` with an unclosed `<think>` as a separate, non-breaker outcome, as in WR-01. Consider a model-capability note in the config docs.

### WR-05: Raid image checks use `FEATHERLESS_MODEL`, which may be text-only, and nothing degrades gracefully

**File:** `xenobot/modules/raid_ai_image.go:113-124`, `:148-160` (client: `xenobot/utils/featherless/classify.go:84-117`)

**Issue:** With `AI_MODERATION_PROVIDER=featherless` (or auto with no Anthropic key), raid image checks call `Classify` with `FEATHERLESS_MODEL`. The AI spam-name rule uses the same variable, and that rule needs only text. The package's own example model, `Qwen/Qwen3-32B` (`featherless/client.go:99`), is text-only according to spike 003. Unlike the reaction path, there is no text-only detection here.

**Failure scenario:** An owner sets a text model for name checks. Every new member's photo now costs an image budget unit, ends in a 400, is recorded by `raidAIImageRecordFailure` and logs a Warn. After five failures the chat's image checks pause, and they keep re-tripping every 5 minutes.

**Fix:** Add a separate `FEATHERLESS_VISION_MODEL`, and set image checks to unconfigured when it is empty, through `raidAIImageConfigured`. Alternatively, apply the corrected text-only latch from WR-02 to the image path, and stop making image calls once it is set. At minimum, change the doc comment example to a vision model.

### WR-06: Cache and thought tokens are dropped, and no provider call logs its duration

**Files:**
- `xenobot/modules/chat_prompt.go:60-65`, `:131`, `:150`, `:155-163`
- `xenobot/modules/chat_run.go:362`
- `xenobot/utils/gemini/response.go:27-33`

**Issue:** The clients parse cache data:
- `gemini.Reply.CacheReadTokens` and `ThoughtsTokens`
- `featherless.Reply.CacheReadTokens` (with a two-shape fallback at `converse.go:184-188`)
- `claude.Reply.CacheReadTokens` and `CacheCreationTokens`

`chatAnswer` has no fields for them, and `chatAnswerOf` takes only input and output. The only success line, `"[Chat] answered (%d input, %d output tokens)"`, carries no cache hit, no thought tokens and no call duration. No path wraps `converse` with `time.Since`.

Gemini's `OutputTokens` is `candidatesTokenCount`, which leaves out the billed `thoughtsTokenCount`, so the logged output count is too low for Gemini.

**Failure scenario:** Operators who report "Gemini or Featherless is slow or expensive" cannot tell from the logs whether:
- the static prefix is being cached (the expected ~12k-token hit)
- thinking is eating the budget (the cause of WR-01)
- the time goes to the provider call or to pacing and media download

**Fix:** Add `CacheReadTokens`, `ThoughtTokens` and `Duration` to `chatAnswer`. Fill them in all three adapters, and measure `time.Since(start)` around `converse` (or `Generate` or `Converse`). Log them on the answered line and at Debug on the reaction, brief and toy paths. IDs and numbers only, as AGENTS requires.

### WR-07: Transport errors are never retried and count toward the breaker

**File:** `xenobot/utils/featherless/client.go:145-162`, `xenobot/utils/gemini/client.go:149-166`

**Issue:** `exec` retries only an `*HTTPError` with `Retryable()`. A connection reset, an EOF on a reused keep-alive connection, or a TLS `bad record MAC` (recorded in spike 003, `PITFALLS.md:106`) fails at once. The caller classifies it as `"transport error"` (`chat_prompt.go:189`) and records a breaker failure. These errors are usually transient and safe to retry, because the request was never processed or the connection dropped before any response.

**Failure scenario:** The pooled keep-alive connection to `api.featherless.ai` goes stale while the bot is idle. The next few calls fail with `EOF` or `connection reset by peer`, each counts as a failure, and an active group pauses after a short burst.

**Fix:** In `exec`, also retry once, after `retryWait`, for transport errors that are not context errors (`!errors.Is(err, context.Canceled) && !errors.Is(err, context.DeadlineExceeded)`) when `ctx` still has time left. Optionally limit this to `io.EOF`, `syscall.ECONNRESET` and `net.Error` timeouts that happen before the response.

## Info

### IN-01: Gemini always sends `thinkingConfig.thinkingLevel`, whatever the model (unverified against provider docs; verify before fixing)

**File:** `xenobot/utils/gemini/request.go:72-79`, `:118-124`; `xenobot/config/config.go:675`

**Issue:** `CHAT_GEMINI_MODEL` accepts any plain model id (`validChatModel` uses `claude.ValidModel`). Every request carries `thinkingLevel: "low"`. My recollection is that Google accepts `thinkingLevel` only on Gemini 3 and later. Gemini 2.5 models take `thinkingBudget`, and 2.0 models reject thinking config, possibly with a 400 INVALID_ARGUMENT.

**Failure scenario (if true):** An owner sets `CHAT_GEMINI_MODEL=gemini-2.5-flash`. Every turn gets a 400, each group pauses on its own, and there is never a provider-wide pause or a clear log.

**Fix:** Verify this. If it holds, omit `thinkingConfig` for model ids outside a known prefix list, or document that only Gemini 4-family models are supported and warn at config time.

### IN-02: Gemini `BLOCK_ONLY_HIGH` may be stricter than the API default (unverified against provider docs; verify before fixing)

**File:** `xenobot/utils/gemini/request.go:24-35`

**Issue:** The comment assumes the default is stricter than `BLOCK_ONLY_HIGH`. As I recall, the default threshold for Gemini 2.0 and later models is `OFF` or `BLOCK_NONE`. If so, these settings add refusals on the archive's black-comedy material, against their stated intent.

**Fix:** Verify against the current safety-settings docs for the configured model. If the default is OFF, either drop `safetySettings` or set it on purpose, and record that it is deliberate.

### IN-03: Featherless concurrency limits versus the bot's parallel callers (unverified against provider docs; verify before fixing)

**File:** `xenobot/utils/featherless/client.go:145-162`, `errors.go:52-60`

**Issue:** One replica can have up to about 8 Featherless calls in flight at once:
- 3 chat workers
- 1 brief worker
- 2 reaction workers
- 2 toy workers

The raid and name pools add more. As I recall, Featherless plans cap concurrent requests. A 429 with no `retry-after` is retried once after 500 ms. It then counts as a group failure, because `chatProviderSpan` returns 0 without a long retry delay.

**Fix:** Verify the plan limits. If they hold, add a per-replica semaphore around Featherless calls (configurable), and treat a 429 that names concurrency as neither a failure nor a success.

### IN-04: Featherless may not honour `max_completion_tokens` (unverified against provider docs; verify before fixing)

**File:** `xenobot/utils/featherless/converse.go:70-75`

**Issue:** The wire field is only `max_completion_tokens`. Some OpenAI-compatible stacks accept only `max_tokens`. If Featherless ignored it, output would have no cap, classify calls could run past the 15 s timeout, and replies would be long. The tests check only that the field is sent (`featherless_test.go:142`).

**Fix:** Check the Featherless API reference. If it is unclear, send both `max_tokens` and `max_completion_tokens`. Featherless is not OpenAI, so sending both does not cause a conflict error there.

### IN-05: Gemini treats some content-related finish reasons as failures

**File:** `xenobot/utils/gemini/response.go:58-65`, `:98-106`

**Issue:** `refusedFinish` leaves out `OTHER`, `LANGUAGE`, `IMAGE_SAFETY`, `IMAGE_PROHIBITED_CONTENT` and `IMAGE_OTHER`. These fall to the default branch as `ErrNoReply` and count as breaker failures (WR-01), although in practice `OTHER` often accompanies a soft content block.

**Fix:** Map the content-policy finishes to `OutcomeRefused`. Map `OTHER` and unknown finishes to a separate empty outcome that does not count against the breaker.

### IN-06: Featherless accepts only `stop`, `length` and `content_filter` (unverified against provider docs; verify before fixing)

**File:** `xenobot/utils/featherless/converse.go:200-211`, `classify.go:179-185`

**Issue:** Backends that report `eos`, `eos_token`, `end_turn` or `stop_sequence` would turn every call into `ErrNoReply` or `ErrNoVerdict`. The tests use only the OpenAI values.

**Fix:** Confirm what Featherless returns. Consider mapping `eos`, `eos_token`, `end_turn` and `stop_sequence` to stop.

### IN-07: Featherless error envelope parsing is all-or-nothing

**File:** `xenobot/utils/featherless/errors.go:82-108`

**Issue:** `Detail` is a `string`. A FastAPI 422 body `{"detail":[{...}]}`, or a gateway body `{"error":"insufficient quota"}`, makes `json.Unmarshal` return a type error. The code then drops every field. `Type`, `Code` and `Message` are lost, so `KeyRejected` cannot see `insufficient_quota` in a string-shaped body: a 429 is retried and pauses one group instead of the whole provider. WR-02's message-based classification would also have nothing to read.

**Fix:** Decode `error` and `detail` as `json.RawMessage` and accept a string, an object or an array.

### IN-08: A 2xx body over 1 MiB is silently cut, then reported as an unreadable answer

**File:** `xenobot/utils/gemini/client.go:198`, `xenobot/utils/featherless/client.go:194`

**Issue:** `io.LimitReader` truncates without signalling. The cut JSON becomes `ErrNoReply "unreadable answer"`, which counts as a breaker failure and gives no hint at the cause.

**Fix:** Read `maxResponseBytes+1` and return a distinct `errors.New("…: answer too large")` when the limit is passed.

### IN-09: The clients accept an empty `Dynamic`, which Anthropic would reject

**File:** `xenobot/utils/claude/converse.go:161-164`, `xenobot/utils/gemini/request.go:119`, `request.go:49-51`

**Issue:** `Converse` and `Generate` check `Static` and `User` but not `Dynamic`. They always send it as a second text block or part: `systemPart.Text` has no `omitempty`. Anthropic answers an empty text block with a 400 "text content blocks must be non-empty". Today every `chatprompt.*Dynamic` returns non-empty text, so this is latent.

**Fix:** Leave out the second block or part when `strings.TrimSpace(in.Dynamic) == ""`, as `featherless.systemPrompt` already does.

### IN-10: Permanent Gemini configuration errors are not provider-wide

**File:** `xenobot/utils/gemini/errors.go:63-73`

**Issue:** A 400 `FAILED_PRECONDITION` such as "User location is not supported for the API use" is permanent for the deployment. It is neither `KeyRejected` nor `Retryable`, so every group trips separately and calls continue forever.

**Fix:** Treat `FAILED_PRECONDITION` as a provider-wide pause in `chatProviderSpan`.

### IN-11: Transcript labels can be spoofed with look-alike characters

**File:** `xenobot/utils/chatprompt/chatprompt.go:147-156`

**Issue:** `Name` adds `(member)` only when the cleaned name contains the exact string `Xenobot-72`. A name that uses U+2011 (non-breaking hyphen), U+2010, a Cyrillic `Х` or `о`, or full-width characters renders as `Xenobot‑72: …`. That line is visually the same as the bot's own transcript lines, which helps a member inject fake earlier bot replies.

**Fix:** Before the comparison, fold the name with NFKC and a small confusables map (hyphens to `-`, Cyrillic look-alikes to Latin). Or label every member line with a fixed prefix the bot never uses, such as `member <name>:`.

### IN-12: `ParseTieBreakerText` flattens lines before the reasoning filter runs

**File:** `xenobot/utils/chatprompt/toys.go:367-370` (consumer `xenobot/modules/chat_polls.go:705`)

**Issue:** `Clean` collapses newlines. Then `chatFilterReply`'s line-anchored `chatFinalMarker` (`(?im)^…final:`) can no longer find a "Final:" line in a leaked draft. A draft that has a final answer but no English cue phrase is posted in full.

**Fix:** Run `chatStripReasoning` (through `chatFilterReply`) on the raw answer first, then apply `ParseTieBreakerText`.

### IN-13: Transport code is copied across three clients, and the copies have drifted

**File:** `xenobot/utils/gemini/client.go:149-219`, `xenobot/utils/featherless/client.go:145-215`, `xenobot/utils/gemini/errors.go:145-155`

**Issue:** `exec`, `send`, `transportError`, `scrub`, `truncateRunes` and `parseRetryAfter` are copied into each package. They already differ: Gemini's `parseRetryAfter` accepts only seconds, while Featherless and Claude also accept an HTTP-date. Fixes such as WR-07 and IN-08 have to be made three times.

**Fix:** Move the shared helpers into one stdlib-only internal package, for example `xenobot/utils/internal/llmhttp`, that all three leaf clients import. This keeps the leaf invariant.
