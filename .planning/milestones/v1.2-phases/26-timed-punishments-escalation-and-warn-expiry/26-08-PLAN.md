## Phase Goal

**As a** group owner, **I want** to make my group's automatic punishments timed, escalate repeat offenders step by step and let old warns
expire, **so that** a first slip costs less than a pattern of abuse, while a group that sets none of this keeps every reply and punishment
exactly as it is today.

This plan builds the ladder's storage and its offence counter, the part that has to be right on every replica at once.

<objective>
Create the two tables of the escalation ladder and the `fuku/db/escalation` repository: the ladder's settings (cached, column-targeted writes)
and the member's offence count (one conditional upsert, shared by every replica, never cached), with their PostgreSQL integrity tests.

Purpose: TUNE-02 says offences count "whichever replica sees them". That rests on a conditional upsert and checks that only PostgreSQL can
prove, so this plan lands them alone, before any site uses them.
Output: one migration, two models, the repository, the `skipLocal` entry, the backup exclusion, and their tests.

Test time budget (D-45): no `fuku/modules` test is added (the harness only migrates the models); the `fuku/db` tests run in `test-rest`.
</objective>

```go
const MaxSteps = 5
const SameOffenceWindow = 60 * time.Second
const DefaultForgetDays = 30
type Step struct { Action string; Secs int }          // mute, tmute, kick, tban, ban; Secs only for tmute and tban
type Ladder struct { Enabled bool; Steps []Step; ForgetDays int } // Steps: step1 up to the first empty one
func ValidStep(s Step) bool                            // the action in the set; a timed one with models.PunishDurationValid; an untimed one with 0
func Get(ctx context.Context, chatID int64) (*Ladder, error)       // cached under chat_escalation:<chat>; no row reads off, no steps, 30 days
func GetFresh(ctx context.Context, chatID int64) (*Ladder, error)
func SetEnabled(ctx context.Context, chatID int64, on bool, by int64) error
func SetEnabledWithSteps(ctx context.Context, chatID int64, steps []Step, by int64) error // on, steps 1..len, the rest cleared
func SetStep(ctx context.Context, chatID int64, n int, s Step, by int64) error            // n 1..MaxSteps; an empty Step clears it
func SetForgetDays(ctx context.Context, chatID int64, days int, by int64) error           // 1..365
func CountOffence(ctx context.Context, chatID, userID int64, now time.Time, forget time.Duration) (int, error)
func ClearOffences(ctx context.Context, chatID int64) error
```

## Planner assumptions (flagged)

- `INSERT ... ON CONFLICT (chat_id, user_id) DO UPDATE SET ... RETURNING offences` with `excluded.` is accepted by PostgreSQL and by the
  SQLite that `go-sqlite3` bundles (3.35 or later). The executor checks this with `TestOffenceCountRules` on SQLite in `make test`. Times are
  unix seconds, so no dialect compares text times.
- SQLite in this suite returns "database is locked" for concurrent writers where PostgreSQL waits (AGENTS.md, the member requirements notes).
  The concurrency subtest of `TestOffenceCountConcurrent` is therefore registered only when the database is PostgreSQL. It is not skipped:
  the case is not added (AGENTS.md: restructure, never `t.Skip`). `TestOffenceCountRules` proves the rules on both databases.
- The constraints are inline in `CREATE TABLE`, because both migration appliers swallow `duplicate_object` on a bare `ADD CONSTRAINT`
  (AGENTS.md, migration 20261120120000's comment).
- A read of a chat with no row returns the default ladder and may cache it; every write drops the key, so a cached default is never stale
  after a write (the `chatconv.Get` pattern).
