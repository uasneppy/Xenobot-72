## Phase Goal

**As a** group owner, **I want** to customize the message for a failed captcha and the notices for member requirement breaches, and to turn on a
rate-limited notice for AI spam deletions, **so that** these messages sound like my community, while a group that sets nothing sees no change.

This plan adds the AI spam notice: new behaviour in `/aispam`'s delete branch, off by default, capped per member and per group, paced fleet-wide.

<objective>
Post the AI spam notice from `processAISpam` after a successful deletion through the engine, with a site whose `Admit` is one Lua script over a per-member
and a per-minute key (fail closed), whose sends go through the notice's own fleet pacer, in the deleted message's topic, queued under `bot:punish_auto`. The
event is off by default through plan 24-02's `OffByDefault`, so a group that never switched it on gets exactly today's behaviour. Reword the `/aispam` help,
which says no notice is ever posted, in all 8 languages and regenerate its doc page.

Purpose: success criterion 3 and EVT-05.
Output: the AI notice site, its limits, the help text, the doc page, the tests and the AGENTS.md lines.

Test time budget (D-40): about 3 s of the phase's 30 s. One aispam dispatcher per subtest with the TypeSafe stand-in; the per-group cap proved with five
members, not a raid; the pacer block fails at once (its slot lies beyond `MaxWait`), so no subtest waits.
</objective>

## Planner assumptions (flagged)

- The script (D-22): `SET KEYS[1] 1 NX EX ARGV[1]` on the member key; when it did not set, return 0; else `INCR KEYS[2]`, `EXPIRE KEYS[2] 120`, and return 1
  when the count is at most `ARGV[2]`, else 0. Both keys carry the hash tag `{<chat>}`, so the script is one round trip under `raidRedisTimeout`. The
  minute is `aispamNoticeNow().Unix()/60`. No client, an error or a refusal is false. The member key is spent even when the group's minute is full: the
  member's next spam inside five minutes stays quiet too (accepted, quieter is the safe direction).
- The site (D-17, D-23, D-26): `Bot` `task.bot`; `Chat` `&task.chat`; `Tr` the group's translator from `task.language`; an empty `Actor`; `ReplyTo` 0;
  `ThreadID` `task.threadID`; `Kind` `bot:punish_auto`; `Automatic` true; `Admit` `aispamNoticeAllow(ctx, task.chatID, task.userID)`; `SendDefault`
  `aispamNoticePaced(poolCtx, ...)` around `helpers.SendMessageWithErrorHandling(task.bot, task.chatID, text, opts)` with `MessageThreadId` set from the task;
  `SendCustom` `aispamNoticePaced(poolCtx, ...)` around `media.SendGreetingMessage(task.bot, task.chatID, msg)`; `poolCtx` is `aispamContext()`, so the
  shutdown drain sheds a wait. The reply: event `aispam`, the target `task.user`, the values (Reason `aispamEventReason(tr)`, Action `eventActionWord(tr,
  "delete")`), the default and its options from `aispamNoticeDefaultReply`. `postAISpamNotice` returns at once when `aispamContext()` is done and logs a send
  error at Debug with the chat and user IDs only.
- `processAISpam` calls `postAISpamNotice(task)` last in its delete branch, only when `helpers.DeleteMessageWithErrorHandling` returned no error, after
  `aispamMirrorDeletion` and `raidAIRecordVerdict`; the keep branch, the failure branch and the breaker are unchanged, and `aispamNotifyBreaker` is not
  touched (its golden). `checkAISpam` copies the effective user into `task.user` and the message's thread into `task.threadID` when the message is a topic
  message; nothing else of the task or of the TypeSafe request changes (`aispamState` is built from the same fields).
- No new shutdown drain (D-23): the notice runs inside an aispam worker, whose drain waits at most `aispamDrainTimeout` (9 s); the pacer's slot wait derives
  from `aispamContext()`, which the drain cancels first.
