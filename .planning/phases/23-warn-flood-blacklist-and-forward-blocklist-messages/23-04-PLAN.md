## Phase Goal

**As a** group owner, **I want** to customize what the bot says when it warns someone, when a member reaches the warn limit, and when flood, a
blacklisted word or a blocked forward gets punished, in the group and by private message, **so that** these messages sound like my community,
while a group that sets nothing sees no change.

This plan switches the remaining four sends to the engine: the warn limit, the flood notice, the blacklist notices and the forward blocklist notice.

<objective>

`postEvent`, each with the site that posts exactly where today's default goes, the builder of plan 23-02, the event values of D-11 and the kept bot
rows of D-15, leaving every inert mode's send untouched; extend the engine guard to the new callers.

Purpose: success criteria 2, 3 and 4 for the send side; the goldens of plan 23-01 prove nothing changes for a group with nothing stored.
Output: four switched sends, their tests, the guard and the AGENTS.md lines.
</objective>

## Planner assumptions (flagged)

- Warn limit: the event branch is taken only when `res.LimitApplied` (the limit action took effect with a known mode); `res.LimitReached` without it is
  the inert mode and keeps today's send exactly (D-10). The site is the warn's (plan 23-02); the values are the warn's reason, `res.Count`, `res.Limit`
  and `eventActionWord(tr, res.Mode)`; the default is `warnLimitDefaultReply` with the target `u`, the count, the limit, `res.Mode` and `res.Reasons`,
  plus the warn's reply parameters; `KeepRows` stays nil (the default's keyboard is empty, so a custom message has no bot row).
- Flood: only `mute`, `kick` and `ban` (of a user or a sender chat) are the event; the inert actions keep today's notice. The target is the sender's user
  (`{Id, FirstName, LastName, Username}`) or, for a sender chat, `{Id: <chat ID>, FirstName: <its title>}`; the values are `floodEventReason(tr)`,
  `floodCrc.messageCount`, `flood.Limit` and `eventActionWord(tr, flood.Action)`; the default is `floodDefaultReply` with the rows today's switch builds
  and `MessageThreadId: msg.MessageThreadId` added to its options; the site has `ReplyTo` 0, `ThreadID` msg.MessageThreadId, `Kind`
  `deletion.KindBotAuto`, `Automatic` true, an empty actor and `SendDefault` `helpers.SendMessageWithErrorHandling(b, chatId, text, opts)` (its nil
  message for a restricted chat is scheduled by nobody, as today); `KeepRows` nil, so the Unmute or Unban row is kept first.
- Blacklist: the three inline blocks become one call of `blacklistNotice` after the punishment, with the action and today's reason
  (`fmt.Sprintf(reason, i)`); the target as for the flood; the values are that reason (escaped by the engine, spliced raw by the default as today), no
  count or limit, and the action word; the default is `blacklistNoticeDefaultReply`; the site has no reply and no thread, `Kind` bot:punish_auto,
  `Automatic` true, an empty actor and `SendDefault` `b.SendMessage(chat.Id, text, opts)`. The warn, none and inert actions are untouched.
- Forward blocklist: `forwardBlockNotice(b, ctx, userID, action)` builds the same site and reply as the blacklist with the reason
  `forwardBlockReason(tr)` and the target from `ctx.EffectiveSender`; `forwardBlockMute`, `forwardBlockKick` and `forwardBlockBan` pass `"mute"`,
  `"kick"` and `"ban"` instead of the template key. Nothing about the source or the Staff Group is in scope there (D-31).
- Each site keeps its own log line and return value on a send error (D-18), and the punishment call stays before the message (D-03).
