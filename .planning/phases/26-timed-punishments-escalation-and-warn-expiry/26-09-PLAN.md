## Phase Goal

**As a** group owner, **I want** to make my group's automatic punishments timed, escalate repeat offenders step by step and let old warns
expire, **so that** a first slip costs less than a pattern of abuse, while a group that sets none of this keeps every reply and punishment
exactly as it is today.

This plan makes the ladder act: the flood, the blacklist and the forward blocklist ask it which punishment a member's offence gets.

<objective>
Add the resolver `escalate` and call it from the three automatic rules right before they punish, so a member's 1st, 2nd and later offences in a
group get the ladder's steps. The rule's own action stays whenever the ladder is off, empty or unreadable.

Purpose: TUNE-02 success criterion 2. The storage of plan 26-08 is in place, and the page (plan 26-10) only writes what this plan reads.
Output: `escalation.go`, the three site changes, and their tests. The ladder is set through the repository in these tests.

Test time budget (D-45): about 3 s of the phase's 35 s (one environment per subtest, real locales only where a default is compared).
</objective>

## Planner assumptions (flagged)

- The resolver runs after each rule's own checks: the exemptions, the bot's restrict right, the deletion of the message, and for the forward
  blocklist the punishment latch. It runs before the request. So nothing the rule refuses today is ever counted, and an album of forwards is
  one count (the latch), as is a burst of blacklist matches inside 60 s (D-26).
- The forward blocklist's notice is reached only through `forwardblock_notice.go`. `forwardBlockPunishTimed` lives in the staff watcher file
  beside its siblings and calls `applyTimedPunishment` and `forwardBlockNotice`; neither is an engine entry or a deletion producer, so
  `TestPMCopyCallers`, `TestMemberDeletionExcludedMessages` and `TestEventEngineCallers` need no new entry. If `TestEventEngineCallers`'s
  allow-list keys a caller by `file: Function` and `forwardBlockNotice`'s key is unchanged, the test passes as it is.
- The golden `noticeGoldenForwardBlock` calls `forwardBlockMute`, `forwardBlockKick`, `forwardBlockBan` and `forwardBlockWarn` as
  `func(*gotgbot.Bot, *ext.Context, int64) error`. They keep that signature and call `forwardBlockNotice(b, ctx, userID,
  autoPunishment{Action: "mute"})` and so on.
- The count write happens before the end date is computed (count, then step, then `punishUntil` inside `applyTimedPunishment`), so the end
  date is still computed right before the request (D-11).
